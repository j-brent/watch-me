# Implementation plan — Harel's watch in Qt Quick + Qt SCXML

**Audience:** Claude Code, working in an empty repo.
**Behaviour spec:** `docs/STATECHART-SPEC.md`, the single source of truth. This plan covers *how* to build it, and the spec defines *what* it does.

## 0. Goal

Build a desktop Qt 6 application that:
1. Implements the **entire** watch statechart from Harel (1987), Section 3, Fig. 31 as one SCXML document, compiled with `qt_add_statecharts`.
2. Renders an interactive **watch** with an LCD, four buttons (a, b, c, d), backlight, beeper and low-battery blink, driven only by that state machine.
3. Renders a **live statechart view** next to the watch. It draws the SCXML hierarchy as literally nested boxes, highlights the active configuration and shows transitions as they fire. This makes it a teaching tool for the paper.

Non-goals: pixel-accurate Citizen artwork, embedded/RPi deployment (keep it portable but don't cross-compile), and statechart editing.

## 1. Step 0 — check the spec against the paper (do this first)

The spec was written without a legible copy of Fig. 31. Rows tagged **[F]** come from memory of the figure and rows tagged **[A]** are assumptions.

1. The paper is committed at `docs/harel1987.pdf` (source: https://www.state-machine.com/doc/Harel87.pdf; the old Edinburgh link is dead).
2. Render Figs. 8–32 to PNG (`pdftoppm -r 200`) and read Fig. 31 closely.
3. Reconcile every [F]/[A] row in the spec. Fix what the figure contradicts, change the tag to [P] where it confirms, and record each change in `docs/DESIGN-NOTES.md` as *row → old → new → figure*.
4. Items most likely to need correction:
   - the update field order and whether a `mode` (12/24h) field exists (T-26)
   - the alarm update fields (T-30..39)
   - whether `a` from `date` does anything (T-15)
   - whether stopwatch is entered via history (§3.5)
   - the chime beep duration (T-71)
   - the exact beep-test entry condition (T-74)
5. If a figure is illegible even at higher resolution, say so. Don't build on unverified [F] rows without saying so in the README.

## 2. Tech stack

| Concern | Choice | Why |
|---|---|---|
| Qt | 6.5 LTS or newer (Core, Gui, Qml, Quick, QuickShapes, Scxml, Test) | `qt_add_statecharts`, QML modules via `qt_add_qml_module` |
| Build | CMake ≥ 3.21, Ninja | standard Qt 6 |
| State machine | **compiled** SCXML (`qt_add_statecharts(watch statechart/watch.scxml)`) generating class `WatchMachine` | type-safe, fails at build time on SCXML errors |
| Datamodel | `datamodel="ecmascript"` | needed for `In()` combined with `T1 != T2` conditions, `delayexpr` time scaling, and `bHeld`/`dHeld` flags |
| C++ standard | C++20 | |
| Tests | Qt Test (`QTRY_VERIFY`, `QSignalSpy`) and a Python conformance script | |

Look up the API details below in the current Qt docs before relying on them. Cite the doc URL in a code comment where an API is non-obvious:
- `qt_add_statecharts` — https://doc.qt.io/qt-6/qtscxml-cmake-qt-add-statecharts.html
- `QScxmlStateMachine::submitEvent`, `isActive`, `activeStateNames(bool compress)`, `connectToState`, `connectToEvent`, `setInitialValues`
- `<send type="qt:signal">` for events that go out to C++/QML, and QML `EventConnection` / `StateMachineLoader` (Qt SCXML QML types)
- SCXML spec, W3C REC 2015: https://www.w3.org/TR/scxml/ (history, `<cancel>`, internal transitions, `In()`)

## 3. Architecture

```
┌──────────────────────── QML (view only, no logic) ────────────────────────┐
│ WatchFace.qml   LCD + buttons + backlight + blink                          │
│ StatechartView.qml   nested boxes from ScxmlTreeModel, active highlight    │
│ SimPanel.qml    clock speed, set T, battery events, event log              │
└───────▲──────────────────────────────▲──────────────────────────▲─────────┘
        │ properties/signals            │ activeStateNames          │ submitEvent
┌───────┴─────────┐   qt:signal   ┌────┴─────────────────┐   ┌────┴──────────┐
│ WatchModel (C++)│◀──────────────│ WatchMachine         │◀──│ ButtonRouter  │
│ time, date, T1, │  increment,   │ (generated from      │   │ (C++) press/  │
│ T2, stopwatch,  │  beep, …      │  watch.scxml)        │   │ release → a.down│
│ 12/24h          │──────────────▶│                      │   └───────────────┘
└─────────────────┘ T.hits.*,     └──────────────────────┘
                    tick.second     ▲ also parsed by ScxmlTreeModel (C++) for the view
```

Rules:
- **All behaviour lives in `watch.scxml`.** C++ only keeps values (time, alarm times, stopwatch counter) and turns time into events. QML only renders and forwards input. A reviewer must be able to delete `WatchModel`'s logic and still see every mode change happen.
- **Data and display are separate.** The statechart view is generated by parsing `watch.scxml` at runtime, with no hand-drawn diagram. Layout hints such as region order go in `statechart/layout.json`, not in QML.
- The SCXML → C++ boundary uses `<send type="qt:signal" event="model.increment"><param name="field" expr="'10min'"/></send>` and similar. List every outward event in `docs/DESIGN-NOTES.md`.
- The C++ → SCXML boundary is `submitEvent("T.hits.T1")` etc. from `WatchModel`, which compares on the second tick.
- The value currently being edited (the update field) is derived from the active state name. The model doesn't track a separate "cursor".

## 5. SCXML conventions

- IDs are global, so use path-like names: `time`, `update_10min`, `alarm1_update_hr`, `sw_run_on`, `alarm1_enabled`.
- Mark every transition with the spec row it implements: `<transition event="d.down" target="date"/> <!-- T-20 -->`.
- Timeouts follow one pattern:
  ```xml
  <onentry><send id="to_date" event="timeout.date" delayexpr="ms(120)"/></onentry>
  <onexit><cancel sendid="to_date"/></onexit>
  <transition event="timeout.date" target="time"/> <!-- T-22 -->
  ```
  with `<script>function ms(s){ return (s*1000*timeScale) + 'ms'; }</script>` and `<data id="timeScale" expr="1"/>`. Tests set `timeScale` through `setInitialValues`.
- The "no button pressed for 2 min" timer restarts with an internal transition on `a.down b.down c.down d.down` that cancels and re-sends the timer.
- Held-button flags live in a root-level `<transition type="internal" event="b.down"><assign location="bHeld" expr="true"/></transition>`, and the same for up/d. These are internal transitions on the root parallel region, so they never change state.
- History: `displays` has `<history type="deep" id="displays_H">`, `stopwatch` has a shallow `sw_H`, and `regular` has a shallow `regular_H` for the beep-test return.
- `clh(main*)` isn't available in SCXML. T-01 enters `alive` through initial states, which gives the same behaviour. Note this in DESIGN-NOTES.
- The `harelAnomalies` flag (`<data>`, default `true`) guards the Fig. 32 behaviour.

## 6. Phases

Each phase ends with a green build and green tests and is one git commit. The phase ID goes in the commit message.

### P1 — Skeleton
CMake project, empty `watch.scxml` with the `dead`/`alive` split, `qt_add_statecharts`, a QML window, and a button that sends `battery.inserted`.
**Accept:** the app launches, the statechart view shows `watch > dead`, and pressing "Insert battery" highlights `alive`.

### P2 — Full SCXML
Implement every spec row. Make the six orthogonal regions of `alive` explicit `<parallel>` children.
**Accept:** `qscxmlc` compiles it without warnings, and `conformance.py` reports every T-xx present in the SCXML.

### P3 — Behaviour tests
Write `tst_watch.cpp` with one check per T-xx using `timeScale = 0.001`. Required scenario tests on top of the per-row checks:
- `b.down` in `update_hr` → `time` **and** `light_on` at once (orthogonality, from the paper)
- alarm fires while in `stopwatch` (lap), any button → back to `stopwatch/lap` (deep history)
- T1 == T2 with both enabled → `both-beep` only
- 30 s of alarm with no button → back to the previous display
- battery dies in `alarm2_update_10min`, re-insert → `time` (cleared history)
- beep-test from `date`, release `d` → `date`
- stopwatch keeps counting while you cycle through other displays and return

**Accept:** all pass, and `conformance.py` reports every T-xx covered by a test.

### P4 — WatchModel
Simulated clock (`QDateTime` base + elapsed × speed), alarm times, stopwatch in centiseconds, field increment rules (sec resets to 0; 1min/10min/hr/mon/date/day/year wrap; date clamps to month length), 12/24h. Emit `T.hits.*` and `tick.second`.
**Accept:** `tst_model` passes; setting T to T1 − 2 s with alarm1 enabled reaches `alarm1_beeps` within 3 simulated seconds.

### P5 — Watch face
`SevenSegment.qml` drawn with QtQuick.Shapes (no font assets). LCD layout per spec §4. Field blink at 2 Hz in update, low-battery blink at 1 Hz, backlight glow when `light_on`, a visual and optional audio beeper (`QSoundEffect`, synthesised tone, off by default).
Buttons: two per side. The default placement is a upper-left, b lower-left, c upper-right, d lower-right [A]; check it against the Citizen manual or Fig. 31's notes and make it a `layout.json` option. Mouse press/release map to `down`/`up`, and keys A/B/C/D work as held buttons so b+d is possible on the keyboard.
**Accept:** every row in spec §4 can be seen by driving the UI.

### P6 — Statechart view
- `ScxmlTreeModel` exposes a recursive tree (id, kind ∈ {atomic, compound, parallel, history, final}, children, outgoing transitions with event/cond/target and spec ID).
- `StateBox.qml` lays out recursively: a compound state is a rounded rectangle with its children inside; a parallel state shows its regions separated by dashed lines, as in Harel. The default child gets a small dot-arrow, a history state is a circled H, and atomic leaves are compact chips.
- Highlight the active configuration from `activeStateNames(false)`. For about 600 ms after a microstep, the source and target of the fired transition flash, and the edge label appears in the event log as `T-xx a.down: time → alarm1`.
- Arrows across nesting levels clutter the view, so draw transitions only on hover or selection of a state, as an overlay with `Shape` paths. The always-on event log covers the rest.
- Zoom and pan, plus collapse/expand per compound state (`layout.json` sets defaults).
- **Legend (mandatory):** each visual channel has exactly one meaning. Fill = active/inactive. Border style = solid compound, dashed AND-region divider. Glyph = default arrow, H/H*. Flash colour = just fired. A small corner badge = spec confidence [P]/[F]/[A], read from the spec.

**Accept:** the whole of Fig. 31's structure is visible at once on a 1920×1080 window, and every button press visibly changes the highlight.

### P7 — Sim panel and polish
Time-speed slider (1×–600×), "set T", "set T to T1 − 5 s", battery weakens/dies/removed/inserted, toggle `harelAnomalies`, and an event log that can be exported as text.
README covers controls, a screenshot, a fidelity section linking DESIGN-NOTES, and the citation of Harel 1987.
**Accept:** a fresh clone builds with `cmake -B build -G Ninja && cmake --build build && ctest --test-dir build`.

### P8 — Verification pass
Re-read the spec and Fig. 31 side by side with the running app. Walk every T-xx by hand using the event log, and record the result in `docs/VERIFICATION.md` as a table: T-xx | steps | expected | observed | ✓/✗.
**Accept:** no ✗ rows, or each one is explained in DESIGN-NOTES.

## 7. CLAUDE.md content (create in P1)

- The spec is authoritative. Change the spec first, then the SCXML, then the tests, in the same commit.
- Keep behaviour out of QML/C++, as in §3.
- Every transition carries a `<!-- T-xx -->` comment, and `conformance.py` must pass.
- Don't hand-edit generated files in `build/`.
- Cite Qt and SCXML doc URLs in comments for non-obvious APIs.

## 8. Risks and mitigations

| Risk | Mitigation |
|---|---|
| Fig. 31 details differ from the spec | Step 0. The spec tags tell you exactly what to check. |
| `qt:signal` send / `EventConnection` behaves differently in your Qt version | Check in P1 with a one-transition spike, and fall back to `connectToEvent` in C++. |
| Simultaneous b+d on a mouse | Keyboard holds, plus a "b+d" convenience button in the sim panel that sends `b.down`, `d.down`. |
| Statechart view gets too dense | Collapse defaults in `layout.json`, edges only on hover, and an always-on log. |
| Real-time delays make tests slow or flaky | `timeScale` via `delayexpr` with `QTRY_VERIFY_WITH_TIMEOUT`. Never sleep fixed amounts. |
| ECMAScript datamodel overhead | Negligible on desktop. If the Pi ever matters, the conditions can move to the null datamodel plus C++ guards. |

## 9. Assumptions made in this plan

- Desktop target only, Qt 6.5+.
- Behaviour follows the paper, not the real watch, where the two differ. Harel himself notes the real watch has quirks (Fig. 32), and those are behind a flag.
- Initial state is `dead` (no battery), so the battery-insert path is visible and tested.
- No audio by default.
- English UI.
